# Fixed-path private pilot policy helper

Preparation only. Nothing here authorizes production access, policy installation, activation, stopping/restarting a service, credential reuse or deployment. Ground Control was unauthenticated during preparation; this helper is not an alternate route around that restriction.

Use only through a separately approved private host-operator channel. The connected tools currently do not provide an authenticated policy-write operation. A root operator needs Node, Docker read access, the reviewed helper/source, and access to the existing private account store. No Google Cloud change, new credential, environment-file copy or private Google-subject export is required.

`policy-helper.mjs` reads JSON from private stdin, never command arguments/workflow inputs. It accepts exactly `email`, `epoch`, `issuedAt`, `expiresAt`, the public approved immutable `image` digest, optional `accessMode`, and `isolationVerified` for apply. The image must use the exact `ghcr.io/teckedd-code2save/unstressed@sha256:…` format, not a mutable tag. The exact approved email must resolve to exactly one existing account with a stored verified Google linkage. Duplicate/missing/unlinked accounts fail closed. All account-ID and Google-subject resolution stays on the host. No private input or account identity appears in output. Do not put real inputs in Git, a workflow, shell history, screenshots or logs.

Default invocation is dry-run; `--apply` is a separate deliberate operator action. Both require root and validate the fixed `/opt/unstressed/data` hierarchy, private file permissions, no aliases/hardlinks, no pending account intent journal, and no existing helper lock. Dry-run does not write a file or acquire a lock. The helper never reads credentials or other app data, edits account data, activates Compose, starts/stops a container or calls a provider.

The policy is installed only at `/opt/unstressed/data/native-pilot-policy.json`. Epoch must exceed the durable ledger and any existing policy, the window is at most 24 hours, and access mode is read-only unless explicitly approved as account-sync. It supports one exact approved identity per operation to keep selection unambiguous. The existing policy must be recognizable; unknown content is not overwritten.

## Avoiding unnecessary downtime

Initial policy preparation may run with web service available if Docker metadata confirms the sole canonical `unstressed-web` data writer uses an immutable image whose locally inspected RepoDigests contains the exact approved image digest and whose `io.unstressed.native-pilot=1` label is present and **exactly** `NATIVE_AUTH_ENABLED=false`. In that state web operations can continue, while native code cannot advance the pilot ledger. The helper inspects only mount/identity/state metadata and a fixed false-flag comparison, never outputs `Config.Env` or secret values. Detected direct/ancestor data-mounting containers, symlink-resolved bind aliases, unknown images or enabled native access fail closed. Docker local bind-driver named volumes and host mount aliases can expose the same data through a different path without a symlink; this bounded metadata inspection does not prove those aliases absent. It deliberately does not scan broad host state or inspect raw volume options, which can contain credentials. Any existing canonical container must carry the explicit false native setting even when stopped, so a later restart cannot implicitly activate the newly installed policy. With no data writer, the same file/journal/permission checks still apply. An authorized operator must establish that no named-volume/host-mount alias, non-container writer or concurrent manual configuration editor can reach the production data during this operation. Apply requires `isolationVerified:true` in the private input as that specific operator assertion. This is not automatic proof or user authorization; do not set it unless the independent checks have actually been completed. Dry-run always reports that this verification is required. If it cannot be established, stop and reconcile before applying; pausing one container alone is insufficient.

The helper captures the immutable image ID and approved repository digest and rechecks container identity/state/image, journal absence, existing-policy contents and selected account/epoch immediately before writing. An exclusive helper lock prevents concurrent helper installs. It uses an exclusive owned temporary file, UID/GID 1000, mode 0600, file fsync, atomic rename and directory fsync. Only its own pre-rename temporary file/lock may be cleaned up. A collision is never deleted. A possibly executed rename or directory-sync failure retains the lock/recovery evidence and is an uncertain outcome: do not retry, delete evidence or activate until reconciled by the approved operator.

If the disabled-writer invariant cannot be established, an explicitly approved maintenance pause is required; this helper will not cause one. Existing journal or storage uncertainty also requires reconciliation, not a workaround. No automatic stopping, restarting, rollback or ledger reset is supplied.

## Eventual operator sequence, not executed

1. Obtain one exact approval covering chosen existing identity, mode, UTC window, native account permissions and planned test operations. Separately confirm the authorized host channel and any required service/configuration change.
2. Deploy the reviewed pilot-capable image with native still pinned false, through the approved existing release process. This does not activate the pilot.
3. Supply the approved private JSON through the authorized operator's private stdin mechanism; run `node deploy/native-pilot/policy-helper.mjs --dry-run`. Review only its identity-free mode/window/epoch result.
4. Only after the policy-write approval, repeat the same privately supplied input with `--apply`. Verify the result says installed and nativeActivated false. A failed/uncertain result is not permission to retry.
5. Activation remains a distinct reviewed explicit Compose/configuration change through that approved channel. The helper cannot perform it. Verify policy availability, then perform the approved device flow. Start with saved-plan comparison and logout; account-sync testing may follow within the same approval if expressly covered.

Local tests cover synthetic accounts/files/writer metadata only. No real identity lookup, policy construction, host inspection, policy write or activation was executed during preparation.
