# Native account sessions (disabled by default)

The initial production release explicitly pins `NATIVE_AUTH_ENABLED: "false"` in `compose.yml`, overriding any unknown value in the runtime environment file. The direct preflight candidate in `deploy/release.sh` also explicitly sets it false. Changing `.env` alone cannot enable native accounts. Later enablement requires a separately reviewed, explicit change to both release controls, coordinated with authorized device and browser acceptance checks; do not remove the pins as routine cleanup. Existing Google OAuth settings and durable account storage must already be configured. No new Google client, callback scheme, production credential or refresh token is introduced. This change does not enable the flag or deploy anything.

## Expo Go compatible flow

1. GET `/api/auth/native/config` returns `enabled`, `sessionLifetimeSeconds` and `pollInterval` (seconds).
2. Generate a cryptographically random PKCE verifier in native memory. POST `/api/auth/native/start` with `{codeChallenge, codeChallengeMethod:"S256"}`. Response: `{flowId,userCode,browserUrl,expiresAt,pollInterval}`. Expiry is epoch milliseconds; flow lifetime is ten minutes.
3. Display `userCode`, open exactly `browserUrl` in the system browser. The page uses the existing Google browser login if needed, displays the signed-in email and matching code, and requires explicit approval. Never approve a link someone else sent. Browser approval is bound to the current browser session and one-time CSRF value. GET never approves access.
4. POST `/api/auth/native/exchange` with `{flowId,codeVerifier}` at the returned interval. Pending is HTTP 202 `{status:"pending"}`. Approval yields `{accessToken,tokenType:"Bearer",expiresAt}` once. Wrong verifier, expired/cancelled/consumed flow fail closed. POST `/api/auth/native/cancel` with the same proof deletes the flow.
Pending polls use a read-only account lookup and do not rewrite or fsync the account file. Approved exchanges revalidate and consume the flow atomically in the durable transaction. Polling quotas are transient in-process state (reset on restart), limited to 40 proof-validated requests per flow per rolling minute, with a separate 4,000-request/minute/IP abuse guard. Invalid flow IDs cannot allocate quota entries; invalid proofs cannot consume another flow’s quota. The 10 starts/minute/IP and ten-minute lifetime bound normal concurrent flows. Cancellation has an independent 120-request/minute/IP budget and bypasses flow polling quotas. HTTP 429 includes Retry-After and is rejected before consuming a flow or issuing a token; retry polling with bounded backoff within the original deadline, but never retry an ambiguous network/5xx exchange automatically.

5. Keep the bearer only in native memory; do not save to AsyncStorage, analytics, URLs or logs. Send `Authorization: Bearer <accessToken>` without Cookie or Origin. Session expires after eight hours; there is no refresh. POST `/api/native/auth/logout` with `{}` revokes this bearer only. Closing the app clears client memory; the server hash expires naturally.

Tokens have an `ust_native_` prefix and are stored only by SHA-256 hash in a separate native session collection. Web cookie sessions cannot authenticate native routes, and native bearer/cookie values cannot authenticate web account or admin routes. Cookie/Origin-bearing native requests are rejected, including a forged trusted Origin. Disabling the feature immediately suspends native access, including existing native sessions, but does not delete stored session hashes. Re-enabling restores any sessions that have not expired or been explicitly logged out; disabling is not permanent revocation. The existing single-writer durable store and uncertain-commit fail-closed semantics apply.

## Scoped API

`/api/native/account` mirrors the existing account current/profile/planning-location, saved plans, circle plans, circles/member edits, invitation inbox/settings and per-plan invitation routes. Request and response shapes use the existing account services, including revision conflicts and live ownership/membership checks. Email invitation sending/acceptance, bookings, execution, shared-day sessions and admin operations are not exposed here. In-app plan invitations still depend on a valid separately configured invitation epoch and only target existing connected accounts.

Only POST `/api/agent` and `/api/itineraries` additionally accept native bearer identity for planning context and server-generated plan saving. Existing plan-id/revision/circle-id headers apply. Expired or revoked bearer fails with 401, never silently falls back to unsaved guest planning. No endpoint accepts uploaded client venue/evidence snapshots. Guest and browser-cookie planning remain supported with unchanged browser Origin/JSON checks.

## Verification before release

Run `node --test backend/test/native-auth.test.js backend/test/accounts.test.js backend/test/account-store.test.js` and the complete backend suite. Use an explicitly authorized staging sign-in to check system-browser Google login, matching code, approval, polling, cancellation, app background/resume, logout, eight-hour expiry, saved revisions, account switching, and circle/invitation revocation. Automated tests substitute identities/provider data; they are not evidence of a real Google or device acceptance test. Do not enable production until those acceptance checks are complete.
