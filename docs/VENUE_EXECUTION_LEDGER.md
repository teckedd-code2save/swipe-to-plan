# Venue execution foundation (non-live)

## What this release does

- Adds `GET /api/actions/execution-capabilities`, returning explicit disabled reasons for calls, messaging, reservations, payments and outbound approval. Existing capabilities remain unchanged.
- Adds internal account-session methods to prepare, read and revoke an owner-private execution record. These methods have **no HTTP mutation routes, model tools or end-user approval UI**. Shared-day bearer keys are not accepted as account identity.
- Stores records alongside, not inside, the saved plan in the existing single-process account store. Plan views, exports and Circle sharing do not contain messages, personal data, approvals or provider references.
- Provides a pure protocol for simulation tests, covering review, approval, atomic outbox reservation, uncertain outcomes and evidence reconciliation. Simulation records and outboxes are explicitly `simulation_only`; they are never usable as live approval.
- Does not read new environment variables, configure providers, request permissions, call/message venues, book, or pay. No rates are embedded.

## Immutable scope and authority

A snapshot binds saved plan ID and revision, exact venue occurrence/item/entity, sourced destination and channel, local date/time/timezone, party, requested operation, exact message, explicit personal-data fields, expiry, total cost limit/currency, effective-dated cost evidence including all fees, and applicable terms/risk evidence. Unknown price remains null. Explicit zero still needs all-fees evidence. Preparing incomplete details grants no authority.

Every mutation is version/hash checked and idempotent within the owner's saved day. Retrying an identical completed request returns the current result only while its version remains current. Changed requests under the same key fail. Plan edits invalidate authority in the same account-store transaction; undo cannot restore it, and forks discard the ledger. The current plan and source are also rechecked before reservation. One pending/unknown/confirmed action for an occurrence or venue entity blocks duplicate submissions across channels, including a moved occurrence. The account service also refuses preparation against the same unresolved entity in another saved day. An unresolved submission or confirmed external reservation prevents deleting its saved day until authenticated reconciliation resolves it. Editing a confirmed plan preserves its evidence and marks it unknown/reconciliation-required. Authenticated cancellation can resolve a confirmed or stale record; accepted events cannot regress confirmation. History capacity never blocks revoke/recover or terminal reconciliation.

The customer mandate, venue-recipient permission and provider eligibility are distinct. `executionBlockers` reports unknown recipient identity, provider eligibility, recipient permission (bound to destination + sender + channel), calling permission, total price verification, and WhatsApp message-policy/window eligibility separately. A published number, a customer approval, a website source check or a manual phone handoff establishes none of those permissions. This function always retains `live_execution_disabled` in this release.

## Protocol and reconciliation

States: `prepared`, `awaiting_review`, `approved`, `submission_pending`, `submitted_awaiting_response`, `submission_unknown`, `provider_confirmed`, `rejected`, `cancelled`.

The production account service admits only prepare/list/revoke. The pure protocol can be constructed in explicit simulation mode to exercise other states with fake adapters. Its methods must run inside the account transaction. They never call any adapter. An outbox is committed before a test driver does a fake side effect, with a stable owner/plan/action/snapshot-scoped key and only approved snapshot data. No tastes, planning-memory context or unrelated profile references are sent to the fake driver.

A restarted `submission_pending` action is treated as unresolved; `recover` marks it `submission_unknown`. Unknown never becomes retryable by a timeout, a new key, changed channel, new approval or plan undo. Cancellation after reservation is not a local status toggle: it needs reconciliation first. No automatic outbox poller or resend loop exists.

The injected synchronous `verifyEvidence` boundary is trusted server code, default-deny, never request/model data. Evidence must bind action, outbox key, snapshot hash, exact venue, date/time/timezone and party, with provider/reference/event identity and a valid event timestamp. Acceptance is not confirmation. Duplicate/reordered events cannot regress state; wrong or unauthenticated confirmation is rejected. Authenticated confirmation of the exact original snapshot after plan changes, expiry, or a newer accepted event is retained as historical external evidence, with `submission_unknown` and an explicit reconciliation requirement. It never newly confirms the current plan and continues blocking duplicate/replacement submissions. An already recorded provider confirmation is not regressed by an older matching confirmation. Delayed confirmation provably preceding a newer authenticated cancellation is retained as cancelled history; a contradictory newer confirmation or one after rejection becomes reconciliation-required instead of being silently discarded. Provider facts already recorded remain historical after plan changes. The existing handoff booking reports stay independent and cannot confer service confirmation or payment authority. There is no public webhook route.

## Remaining prerequisites before any live execution

1. Select an eligible provider/account/product and verify current billing status and complete effective-dated pricing, including transport, AI, template/calling fees and limits. Historical trial notices are not current billing evidence. No blanket free-tier assumption is valid.
2. Resolve and verify the intended venue recipient, sender business/number, allowed channel and operation. Obtain independently verifiable recipient messaging/calling permission and message-category/window/template compliance where required. Resolve AI-provider eligibility. Unknown, expired or unsupported evidence must block dispatch independently of customer approval.
3. Build and review a real adapter and a separate authenticated customer approval surface. Do not enable the simulation protocol in production or reinterpret historical handoff clicks as consent. Revalidate current evidence, cost, expiry, revocation and immutable details atomically at the dispatch boundary.
4. Add a server-only dispatcher with durable claim/recovery semantics, provider idempotency and authenticated evidence verification/reconciliation. Never automatically retry an ambiguous write. Cancellation and rescheduling need their own exact approvals and provider semantics. Before exposing live reconciliation, implement bounded durable evidence/idempotency retention and authenticated-ingress limits: the offline protocol deliberately allows terminal reconciliation beyond ordinary history limits so a confirmation or cancellation is not discarded. Distinct authenticated terminal events can currently grow that simulation history without bound. Do not solve this with a hard cap that strands an external reservation.
5. Harden persistent storage for the live side-effect boundary. Account snapshots now have file/directory fsync, durable intent, write blocking on ambiguity and explicit reconciliation (see `ACCOUNT-DURABILITY.md`). This is not multi-process locking or a guarantee about unverified host storage. A live driver still requires runtime filesystem verification, dispatch-scoped durable idempotency and fault-tested recovery at the external side-effect boundary. Keep the existing single-process deployment.
6. Payments remain a separate disabled capability with their own approval, provider, security and reconciliation requirements.
